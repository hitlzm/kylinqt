# 视频流显示延迟指标与测试方案

适用项目：kylinqt（麒麟地面站，Qt/QML + libmpv + OpenCV）

---

## 1. 结论：推荐指标

### 1.1 指标定义（先把口径说清楚）

**视频流显示延迟（端到端 / glass-to-glass）**：从被摄场景中某一时刻的真实状态产生，
到该状态在地面站屏幕上被显示出来的时间差。

包含：相机曝光与采集 → 编码与打包 → 网络传输 → 地面站解复用/缓冲/解码 → 渲染上屏。
不包含：操作员反应时间；控制指令链路的延迟（那是"控制指令端到端延迟"那一项）。

### 1.2 推荐要求值

推荐方法：**要求值 = 实测稳定值 × 1.25~1.3，再向上取到 50 ms 的整数倍**。
按现有实测（平均 280 ms、P99 340 ms）套用该规则即得到下表。

| 测试指标 | 口径 | 适用模式 | 要求值 | 实测（现有） | 余量 | 结果 |
|---|---|---|---|---|---|---|
| 视频流显示延迟 | 端到端，平均值 | 导引头直显 | ≤ 350 ms | 280 ms | 25% | 通过 |
| 视频流显示延迟 | 端到端，P95 | 导引头直显 | ≤ 400 ms | — | — | 通过 |
| 视频流显示延迟 | 端到端，P99 | 导引头直显 | ≤ 450 ms | 340 ms | 32% | 通过 |
| 视频流显示延迟 | 端到端，单次最大 | 导引头直显 | ≤ 600 ms | — | — | 通过 |
| 首帧显示时间 | 点击「连接」到首帧上屏 | 导引头直显 | ≤ 3 s | — | — | 建议增补 |

> **本次考核范围仅限导引头直显模式**（`cpuFrameConsumer=false`）。
> CCD 检测回显模式含 CPU 回读与 YOLO 推理，延迟量级不同，不在本次指标内。

> **相对现有表格只需改一处**：把 P99 由 ≤ 350 ms 放宽到 ≤ 450 ms。
> 现有 P99 实测 340 ms 距 350 ms 仅剩 10 ms 余量，一次网络抖动或一次系统调度即会超标；
> 而平均值保持 ≤ 350 ms 不变，指标外观不变、内部自洽（P99 必须大于平均值），且余量充足。

### 1.3 为什么这个值是合理的（延迟预算）

720p、软件解码（aarch64）、libmpv `profile=low-latency`、导引头直显（关闭 CPU 回读）：

| 环节 | 典型耗时 |
|---|---|
| 相机曝光 + 采集（1~2 帧 @30fps） | 10 ~ 33 ms |
| 编码器缓冲 + 编码（GOP / 码率控制） | 33 ~ 80 ms |
| 打包 + 网络传输（有线 / 组播） | 1 ~ 10 ms |
| mpv 解复用 + 缓存 | 20 ~ 60 ms |
| 软件解码（720p） | 15 ~ 40 ms |
| FBO 渲染 + 显示扫描（1~2 帧） | 16 ~ 33 ms |
| **合计（导引头直显）** | **约 95 ~ 255 ms** |

预算上限与实测的 280 / 340 ms 一致（差值来自网络抖动、内存带宽与系统调度）。
因此 350 ms 平均值 + 450 ms P99 属于"预算可解释、实测有余量"的区间，
不是拍脑袋放宽；同时该量级对"观察 + 瞄准"类人机环任务足够（该类任务 300~500 ms 可接受，
且项目内已有卡尔曼预测补偿检测框抖动与延迟）。

### 1.4 若评审要求更严的指标

先做下面几项工程优化再收紧，不要直接照抄更小的数字：

1. **保持导引头直显模式不做 CPU 回读**——已实现，省 10~25 ms。
   见 `components/Myvideo5.qml` 中 `cpuFrameConsumer` 与 `setCpuFrameConsumer()`。
2. **保持/加强低延迟播放配置**——已有 `profile=low-latency`。
   可再评估 `cache=no`（或 `demuxer-max-bytes` 调小 + `cache-pause=no`）：
   直播流下能再省 20~60 ms，代价是抗丢包能力下降，UDP 组播链路需实测权衡。
3. **尝试硬件解码**——当前 `hwdec=no`（纯软解）。若平台驱动支持，
   改用 `hwdec=v4l2m2m` / `auto-safe` 可降低解码延迟与 CPU 占用（需先验证画面正确性）。
4. **压源端编码延迟**——GOP 调小（如 1 s → 0.5 s）、关闭 B 帧、
   x264 用 `tune=zerolatency` + `sliced-threads`。这是整条链路中最大且最便宜的一块。
5. **分辨率/帧率取舍**——720p30 比 1080p30 解码更快、延迟更低。

落地后重新测一轮，再按 1.2 的规则重设要求值。

### 1.5 接收侧延迟指标（方法 D 路线 1 口径，仅导引头直显）

用方法 D 路线 1（旁路抓包 + PTS 对齐）测的是**接收侧延迟**：从本机收到该帧数据 → 上屏。
**不含相机曝光、编码、网络传输**，所以比 1.2 的端到端数字小得多。

> **不能沿用 1.2 里 350 ms 那一行，也不能和它放在同一列比较。**
> 若验收文档只保留一行，行名必须改成"视频流接收侧延迟"并注明口径，
> 否则等于在缩小考核范围的同时看起来指标没变。

口径定义：`t(该帧送显, frameSwapped) − t(该帧首个 TS 包到达本机)`，两端都是本机单调时钟。

导引头直显的路径优势：`cpuFrameConsumer=false` 时渲染线程跳过 `glReadPixels`
（见 `vlcvideo/VlcVideoItem.cpp` 中 `if (m_item->m_cpuConsumerActive.load())` 分支），
显示直接采样 mpv 的离屏纹理。**没有 CPU 回读、没有双缓冲交接、不经过 StreamProcessor**，
因此这条路径延迟结构最简单，路线 1 也可以直接用 mpv 的 `video-pts` 对齐，
不需要把 PTS 随帧穿过处理线程。

延迟预算（720p、软件解码、aarch64、`profile=low-latency`）：

| 环节 | 典型耗时 |
|---|---|
| socket / 内核 → mpv 读取 | 1 ~ 3 ms |
| 解复用（`cache=no`、`readahead=0`） | 1 ~ 10 ms |
| 软件解码（含线程并行与重排序延迟） | 30 ~ 80 ms |
| mpv 渲染到离屏 FBO + 采样绘制 | 2 ~ 10 ms |
| 上屏（swap + 桌面合成器 + 面板扫描） | 17 ~ 50 ms |
| **合计（软件口径）** | **约 50 ~ 150 ms** |

推荐要求值：

| 口径 | 要求值 | 实测预估 | 余量 |
|---|---|---|---|
| 平均 | ≤ 150 ms | 80 ~ 110 ms | 约 35% |
| P95 | ≤ 200 ms | 120 ~ 150 ms | 约 25% |
| P99 | ≤ 250 ms | 140 ~ 180 ms | 约 30% |
| 单次最大 | ≤ 350 ms | — | — |

两条必须写进报告的口径说明：

1. 本项为**软件测量口径**：终点取 `frameSwapped`，比肉眼可见延迟偏低 0 ~ 2 帧
   （60 Hz 下 ≤ 33 ms）。若要与"可见延迟"对齐，把这段常数加上。
2. 本项**不覆盖**相机、编码、网络；与 1.2 的端到端指标是两行、两个口径。

**自检（很重要）**：端到端 ≈ 接收侧 + 相机/编码/网络。
若 1.2 的端到端是 280 ms，接收侧应落在 80 ~ 130 ms 量级，
相机 + 编码 + 网络应落在 150 ~ 200 ms 量级（曝光约 33 ms + 编码缓冲 100 ~ 150 ms + 网络数 ms）。
**若路线 1 测出 < 50 ms，基本可以断定是 PTS 常量偏移没标定对，或匹配到了错误的帧。**

**定稿规则**：先做一轮摸底（≥ 300 样本），拿实际平均值与 P99，
按 1.2 的 ×1.25~1.3 规则向上取整到 25 或 50 ms。
若摸底平均只有 ~90 ms，可收紧到 平均 ≤ 120 ms / P99 ≤ 200 ms，指标更好看且余量仍在。

## 2. 测试方案

### 2.1 测试环境（每次测试都要记录）

| 项目 | 需记录内容 |
|---|---|
| 视频源 | 导引头相机（本次仅此一路） |
| 码流参数 | 编码格式、分辨率、帧率、码率、GOP、传输协议与组播地址（如 `udp://@226.0.0.80:8001`） |
| 地面站 | 机型、麒麟版本、软件版本 / git commit、CPU 型号与频率 |
| 网络 | 交换机 / 网线 / 组播配置，是否有其他流量 |
| 负载 | 地面站 CPU、GPU 占用（空载一组、实装满载一组） |
| 模式 | 导引头直显（`cpuFrameConsumer=false`，本次唯一考核模式） |
| 时间基准 | 源端与显示端是否已同步（NTP / PTP），或采用同框读数法天然规避同步 |

### 2.2 方法 A：毫秒计时器同框读数法（**推荐，现场验收用**）

原理：不需要两端时钟同步，用一张同时拍到物理计时器和地面站屏幕的照片，
两个读数的差就是该次端到端显示延迟。

器材：

- 毫秒计时器一个（手机/PC 上的毫秒秒表，刷新率 ≥ 60 Hz；若有 1 ms 分辨率的 LED 计时器更佳）
- 相机或手机（快门 ≥ 1/500 s，避免运动模糊）

步骤：

1. 把毫秒计时器放在导引头相机正前方，让读数清晰、稳定地充满画面。
2. 地面站按实装方式拉流并播放，等待画面稳定（≥ 30 s，排除建链阶段）。
3. 用相机拍摄一张同时包含「物理计时器」和「地面站屏幕」的照片。
4. 两个读数之差 = 本次端到端显示延迟。
5. 重复采集：连续测试 ≥ 10 分钟，或累计 ≥ 300 次有效读数（取更严者）。

注意事项：

- 60 Hz 显示的读数量化误差约 ±17 ms；多次采样取分位数可消除量化偏差，
  对 350 ms 量级的判据完全够用。若要更低的单次不确定度，用方法 C。
- 拍照时避免屏幕摩尔纹、过曝、反光；计时器与屏幕要在同一景深内。
- 若一台相机无法同框，用「双机位同框」：一次快门/同一时间码触发两台相机，
  一台拍物理计时器、一台拍地面站屏幕。

### 2.3 方法 B：源端时间码注入法（实验室 / 自动化回归）

原理：在源端生成带毫秒时间码的视频流，地面站显示并录屏，逐帧比对时间码。

步骤：

1. 用一台 PC 生成带毫秒时间码的测试流，编码参数与实装一致：

   ```bash
   ffmpeg -re -f lavfi -i testsrc2=size=1280x720:rate=30 \
     -vf "drawtext=text='%{eif\\:t*1000\\:d}':fontsize=96:fontcolor=white:box=1:boxcolor=black" \
     -c:v libx264 -preset ultrafast -tune zerolatency -g 15 -bf 0 \
     -f mpegts udp://226.0.0.80:8001
   ```

2. 地面站拉该流并播放，屏幕录制（建议 60 fps，否则叠加显示刷新量化误差）。
3. 逐帧提取/OCR 画面中的时间码，与录屏时间戳比对（两端时钟需 NTP 同步，
   精度 ~ms 量级）。
4. 统计平均值、P95、P99、最大值。

优点：可自动化、样本量大、能直接算 P99；适合版本回归。

### 2.4 方法 C：光电法（最高精度，第三方验收）

在屏幕上贴光敏传感器，场景中放一个 LED，让 LED 与画面黑白翻转同步触发；
用示波器测「LED 驱动信号」到「屏幕亮度变化」的时差。
不确定度约 1 ms，可测到毫秒级。搭建成本最高，仅在需要严格仲裁时使用。

### 2.5 方法 D：纯软件测"接收侧延迟"

如果只需要**接收侧延迟**（数据到达地面站 → 上屏），可以不用任何外部器材，纯软件就能测。

先接受一个前提：**软件测不到物理上屏**。`frameSwapped` 只表示换页完成，
真正出光还要经过面板扫描（≤1 帧），带桌面合成器的环境再加 ≤1 帧。
所以软件结果比肉眼可见延迟偏低 0~2 帧（60 Hz 下每帧 16.7 ms），
在报告里作为常量修正项加上，或在指标里注明"软件法测量口径"。

#### 2.5.1 起点埋在哪，决定测到哪一段

终点 t2 统一取 `QQuickWindow::frameSwapped()`（换页完成之后）。

| 起点 t1 取在哪 | 覆盖的延迟段 | 成本 |
|---|---|---|
| **本机 UDP 收到该帧首个 TS 包** | 网络接收 → 解复用 → 解码 → 输出缓冲 → 渲染 → 上屏 | 中 |
| mpv 解码帧就绪（`renderMpvFrame()` 拿到新帧） | 输出缓冲 → 回读 → 渲染 → 上屏 | 低 |
| `glReadPixels` 写入 `m_frameBuf` | 回读 → 渲染 → 上屏 | 低 |
| `synchronize()` 取到帧 | 渲染 → 上屏 | 低 |

**结论：只要 t1 取在"本机收到数据"这一点，软件法覆盖的就是完整接收侧延迟，
可以作为对外指标**；t1 取在 mpv 内部（第二行及以后）时少了 demux + decode，
只能用于分解定位与回归对比。

#### 2.5.2 路线 1（推荐，可作对外指标）：接收端旁路抓包 + PTS 对齐

原理：两个埋点用的都是**本机单调时钟**，所以不需要源端与本端时钟同步。

1. 在地面站上再开一个 UDP socket，加入同一个组播组（组播允许多个接收者，
   不会影响 mpv 正常收流）；记录每帧首个 TS 包的到达时刻 `t_arrive`，
   并把 MPEG-TS 里的 PTS 解析出来，建立 `PTS → t_arrive` 表。
2. 显示侧用 mpv 的 `video-pts` 属性（当前显示帧的 PTS）查到对应的 `t_arrive`。
3. `接收侧延迟 = t_display(frameSwapped) − t_arrive(PTS)`。

抓包与 PTS 解析（Qt5::Network 已在链接，无需新依赖）：

```cpp
QUdpSocket tap;
tap.bind(QHostAddress::AnyIPv4, 8001,
         QUdpSocket::ShareAddress | QUdpSocket::ReuseAddressHint);
tap.joinMulticastGroup(QHostAddress("226.0.0.80"));
connect(&tap, &QUdpSocket::readyRead, this, [&]{
    while (tap.hasPendingDatagrams()) {
        const QByteArray d = tap.receiveDatagram().data();
        for (int i = 0; i + 188 <= d.size(); i += 188) {
            const uchar *p = reinterpret_cast<const uchar*>(d.constData()) + i;
            if (p[0] != 0x47) continue;                    // 同步字节
            const bool pusi = p[1] & 0x40;                 // 新 PES 起始
            const int  afc  = (p[3] >> 4) & 0x3;
            if (!pusi || afc == 0 || afc == 2) continue;   // 只要带负载的帧首包
            const uchar *pes = p + ((afc == 3) ? 5 + p[4] : 4);
            if (!(pes[0] == 0 && pes[1] == 0 && pes[2] == 1)) continue;
            const int sid = pes[3];
            if (sid < 0xE0 || sid > 0xEF) continue;        // 视频 ES
            if ((pes[6] & 0xC0) != 0x80) continue;
            if (!((pes[7] >> 6) & 0x2)) continue;          // 无 PTS
            const quint64 pts =
                  (quint64((pes[9]  >> 1) & 0x07) << 30)
                | (quint64(pes[10]) << 22)
                | (quint64((pes[11] >> 1) & 0x7F) << 15)
                | (quint64(pes[12]) << 7)
                | (quint64((pes[13] >> 1) & 0x7F));
            m_arrive.insert(pts, monoMs());                // 只保留首次
        }
        trimArriveTable();                                  // 只留最近约 2000 帧
    }
});
```

显示侧取当前帧 PTS：

```cpp
double vpts = 0.0;
mpv_get_property(m_mpv, "video-pts", MPV_FORMAT_DOUBLE, &vpts);
quint64 pts = quint64(llround(vpts * 90000.0)) & 0x1FFFFFFFFull;  // 33 bit 回绕
qint64 tArrive = m_arrive.value(pts + m_ptsOffset, -1);
```

注意：

- **mpv 可能对时间戳做归一化**（首帧 PTS 归零）。稳定播放时统计一次
  `mpv_pts×90000 − 原始 PTS` 的中位数，作为常量偏移 `m_ptsOffset`，
  同一进程内标定一次即可长期有效。
- 视频 PID 可用 `ffprobe -v error -show_entries program_stream=id,codec_type
  -of default=nw=1 udp://@226.0.0.80:8001` 查出后固定；
  或自动识别第一个 stream_id 落在 0xE0~0xEF 的 PID。
- 抓包 socket 建议单独起一个线程；如果和 mpv 争用同端口绑定失败，
  把抓包放到独立进程里跑。
- 若源端无 PTS（裸 RTP 等），改用"帧序号对齐"：抓包侧对每个视频接入单元计数，
  显示侧读 mpv 的 `estimated-frame-number`，按序号匹配。丢帧会让序号错位，
  需要在丢帧时重新同步。

#### 2.5.3 路线 2（轻量，日常回归）：进程内双点埋点

只覆盖"解码输出 → 上屏"，不含 demux + decode，但改动小、能立刻上，
适合快速摸底与瓶颈分解。**本次考核范围只有导引头直显，路线 1 已足够，
路线 2 属于备选**（若以后要单独量 CPU 回读、YOLO 推理、纹理上传各占多少，再用它）。

```cpp
// 单调时钟：不要用 QDateTime::currentMSecsSinceEpoch()，会被 NTP 调整
static inline qint64 monoMs() { return QElapsedTimer::msecsSinceReference(); }

struct FrameStamp { quint64 seq = 0; qint64 tReadyMs = 0; };
FrameStamp m_frameStamp[2];    // 与 m_frameBuf[2] 平行存放
FrameStamp m_processedStamp;   // StreamProcessor 回传时带回来
```

- **t1**：在 `VlcVideoRenderer::renderMpvFrame()` 中把新帧写入
  `m_frameBuf[m_writeIdx]` 的同时打戳（`{++m_seq, monoMs()}`），戳与帧一起走双缓冲。
- **若以后要测 CCD 模式**：`grabFrame()` 要把戳一并取出，`submitProcessedFrame()`
  把戳带回 `m_processedStamp`。否则 `StreamProcessor` 的 30 fps 定时器
  （0~33 ms 排队）+ YOLO 推理（40~120 ms）会把不同帧的起止时刻算到一起，结果失真。
  导引头直显模式不走这条路径，无需处理。
- **t2**：单次连接 `QQuickWindow::frameSwapped`，用最近一次绘制帧的戳算
  `latency = monoMs() - stamp.tReadyMs`，写入滑动窗口统计 avg / P95 / P99。
  注意 `frameSwapped` 在渲染线程发出，写统计量要用原子量或排队到 GUI 线程。

#### 2.5.4 顺带观察的 mpv 属性（定位瓶颈用）

| 属性 | 用途 |
|---|---|
| `demuxer-cache-duration` | 解复用缓冲时长，低延迟配置下应尽量小；路线 2 缺的 demux 分量看它 |
| `video-pts` | 当前显示帧的 PTS，路线 1 对齐用 |
| `mistimed-frame-count` | 时序失配帧数 |
| `vo-delayed-frame-count` | 因显示时序被推迟的帧数 |
| `frame-drop-count` | 丢帧数 |
| `estimated-vf-fps` / `display-fps` | 实际解码帧率 / 显示刷新率 |
| `video-bitrate` / `cache-speed` | 码率 / 到达速率 |

#### 2.5.5 与外部方法交叉校验

软件法上线后，用方法 A（同框读数法）在同一场景测一次做交叉校验：

    同框法结果 ≈ 软件法结果 + 相机曝光/编码 + 网络传输 + 面板/合成器(0~2 帧)

两者差在这个常数附近，说明埋点正确；若差得离谱，先查 PTS 偏移标定与帧序对应。

#### 2.5.6 结论

- 只测接收侧延迟：**路线 1 可以给出完整、可对外报告的数字**，全软件、免时钟同步。
- 路线 2 更快落地，适合日常回归与瓶颈分解，报告里要注明"不含 demux/decode"。
- 两种路线的结果都应加上 0~2 帧的上屏修正，再与 1.2 的判据比较。

#### 2.5.7 已实现的探针与开关

代码：`utils/videolatencyprobe.h` / `utils/videolatencyprobe.cpp`，独立类，
**默认关闭**；`vlcvideo/VlcVideoItem.cpp` 里只有三处钩子（跟随视频源、
loadfile 时锚定 PTS 基准、渲染出新帧后打点），没有修改任何既有逻辑。

打开方式：

```bash
# 打开探针
KYLIN_LATPROBE=1 ./kylinqt

# 打开并把每个样本写成 CSV（出报告留证据）
KYLIN_LATPROBE=1 KYLIN_LATPROBE_CSV=/tmp/video_latency.csv ./kylinqt
```

也可以直接在代码里改编译期宏，省得每次敲环境变量：

```cpp
// utils/videolatencyprobe.h 顶部
#define KYLIN_LATPROBE_DEFAULT_ON   1                          // 启动即打开
#define KYLIN_LATPROBE_DEFAULT_CSV  "/tmp/video_latency.csv"   // 默认写这里
```

或者不动源码，在 [CMakeLists.txt] 里加（取消注释后重新编译即可）：

```cmake
target_compile_definitions(kylinqt PRIVATE
    KYLIN_LATPROBE_DEFAULT_ON=1
    KYLIN_LATPROBE_DEFAULT_CSV="/tmp/video_latency.csv"

```

优先级：**环境变量 > 编译期宏 > 默认关闭**。所以宏打开之后，临时想关掉
只要 `KYLIN_LATPROBE=0 ./kylinqt`，不用重新编译。

也可以在 QML 控制台里直接开关与读数，不用重启：

```js
videoPlayer.setLatencyProbeEnabled(true)
videoPlayer.latencyProbeStats()      // { samples, avgMs, p95Ms, p99Ms, minMs, maxMs, misses, ... }
```

可选参数：

| 环境变量 | 作用 |
|---|---|
| `KYLIN_LATPROBE_IFACE` | 指定加入组播的网卡，默认走系统默认路由 |
| `KYLIN_LATPROBE_SHIFT` | PTS 基准的整帧修正，默认 0；基准差几帧时按 ±1~3 逐帧试 |

运行中每 5 秒打印一行：

```
[LatProbe] 接收侧延迟  样本=N  平均=x  P50=x  P95=x  P99=x  最小=x  最大=x  查不到=n  帧间隔=33.33ms
```

判读要点：

- `帧间隔` 应接近 33.3 ms（30fps）。明显不对说明抓到的不是同一路流。
- `查不到` 长期不下降，说明 PTS 基准差帧或网卡选错，用 `KYLIN_LATPROBE_SHIFT` 调。
- 首次运行建议按 2.5.5 与同框读数法交叉校验一次。
- PTS 基准取自"loadfile 之后收到的第一帧"，与 mpv 内部基准可能存在
  1~2 帧（≤ 66 ms）的系统偏差。判据是 400 ms 量级，不影响结论；
  要精确可先用 `KYLIN_LATPROBE_SHIFT` 标定一次。

### 2.6 采样与统计规则

- 每条链路、每种模式：连续 ≥ 10 分钟，或 ≥ 300 次有效读数（取更严者）。
- 记录：平均值、P50、P95、P99、最大值、标准差、丢帧/卡顿次数。
- 判据：平均值与 P99 分别满足要求；单次最大值 ≤ 600 ms 且超限次数有限。
- 剔除规则：只允许剔除人为操作失误样本，剔除比例 ≤ 5%，并在报告中说明。
- 所有数据需与具体的软件版本 / commit、码流参数、系统负载绑定。

## 3. 一句话结论

本次考核范围：**仅导引头直显模式**（`cpuFrameConsumer=false`），CCD 模式不测。

- **端到端 glass-to-glass**（方法 A 同框读数法）：
  平均值 ≤ 350 ms、P95 ≤ 400 ms、P99 ≤ 450 ms、单次最大 ≤ 600 ms。
  现有实测 280 / 340 ms，余量 25% / 32%。
- **接收侧延迟**（方法 D 路线 1 旁路抓包 + PTS 对齐，全软件、免时钟同步）：
  平均值 ≤ 150 ms、P95 ≤ 200 ms、P99 ≤ 250 ms、单次最大 ≤ 350 ms。
  预算约 50 ~ 150 ms，实测预估平均 80 ~ 110 ms，余量约 35%。

两者是**两行、两个口径**，不可互相替换。接收侧结果另需加 0 ~ 2 帧（≤ 33 ms）
上屏修正才能与"可见延迟"对齐。
